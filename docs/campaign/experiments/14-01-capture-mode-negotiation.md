# EXP-1401 Capture-mode negotiation read-back (WT-10 E-1)

- Hypothesis: pinning an explicit capture backend and asserting the READ-BACK mode (W/H/FOURCC/FPS) against the request turns the OS's silent mode swaps (e.g. Windows UVC "MJPEG at source autodecode" substituting decoded NV12/YUY2) into an explicit DEGRADED health state with exact values, instead of a silent quality change. The user requirement forbids lowering camera resolution as a speed fix — so the negotiated mode must be verified at full request (1280x720@30 MJPG, YUY2 fallback), never quietly reduced.
- Requirement link: user "highest useful stable capture quality with verified negotiated modes" -> F-03 (camera source resolution), F-38 (camera health).
- Baseline: commit e86d34b5d16abcc133ad3470c8d135d00b2423d4; backend/pipeline_capture.py open() used CAP_ANY for live device indices, requested 1280x720@30 with no FOURCC request and no read-back assertion; cv2 4.10.0 with DirectShow=YES MediaFoundation=YES (WT-10 measured); machine has NO physical camera — virtual dshow devices present (DroidCam / Windows Virtual Camera / NVIDIA Broadcast / OBS Virtual Camera, WT-10 P-6); source mode: virtual camera + scripted fakes.
- Candidate: commit e7dc49e (+7e4e5d6 api wiring); CaptureProfile (config/camera_profiles.yml) pins backend dshow|msmf, requests 1280x720@30 MJPG + YUY2 fallback, verify_negotiated_mode() compares read-back with 1% fps tolerance, mismatch -> capture_state "mode-mismatch", health DEGRADED + exact log line "Capture mode negotiation mismatch for <id>: requested=WxH@fps FOURCC actual=WxH@fps FOURCC mismatched=fields".
- Success criteria (defined BEFORE inspecting results): (a) every scripted silent-swap (NV12/YUY2 substitution, W/H/FPS drift) is detected, mismatched_fields exactly right, exact log line emitted; (b) YUY2 fallback acceptance is distinguished from mismatch (fallbackUsed=true, modeMismatch=false); (c) a real virtual-device probe records actual negotiated modes for CAP_DSHOW and CAP_MSMF or records that no device opened; (d) zero cases where a mismatch is silent.
- Failure criteria / rollback: any silent mismatch (mismatched mode with no DEGRADED/health/log evidence) rejects the candidate; revert commits e7dc49e/7e4e5d6.
- Result: MEASURED (batch 02:26:04-02:27:00, atomic-RESOURCE-LOCK window; Contention label per Main arbitration 2026-09-29: latency-sensitive figures are POTENTIALLY CONTENDED (WT-19 hold-timestamp dispute over the 02:23-02:27 window; deterministic byte totals/counts stand as measured).; artifact: reports/wt14-measure-raw.txt (raw batch output, 33,889 bytes, SHA-256 c923a61f1e3c5abbdf4871e700558e9f65274369b3323552f21eb3efeb2651ba)): real virtual device at dshow index 1 opened via CAP_DSHOW, frame read OK (720,1280,3) — requesting 1280x720@30 MJPG read back {width:1280, height:720, fps:30.00003, fourcc:'YUY2'}: the MJPG pin was silently refused and the OS/driver landed on YUY2 at FULL requested resolution/fps — exactly the silent-swap trap, now classified fallbackUsed=true / modeMismatch=false by design (YUY2 is the configured acceptable fallback). dshow indices 0/2: not opened (OpenCV warns the backend "can't be used to capture by index" for those); msmf indices 0-3: not opened. Behavioral acceptance (a)+(b)+(d): 33-case scoped suite green (test_silent_mjpeg_swap_is_degraded_with_exact_log asserts the EXACT log line "Capture mode negotiation mismatch for CAM-01: requested=1280x720@30.0 MJPG actual=1280x720@30.0 NV12 mismatched=fourcc"; drift and fallback cases in the same file). n=4 device indices x 2 backends probed; 1 device opened. ffmpeg dshow enumeration NOT RUN in the batch (script resolved the binary path incorrectly, exists=False — failure preserved); WT-10 P-6 rows remain the device-mode reference.

- Cold vs warm: virtual-device opens are cold (device init included); scripted-fake assertions have no timing content (behavioral only).
